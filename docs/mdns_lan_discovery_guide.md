# DinoRoar 局域网服务发现技术指南

本指南详细记录了在 DinoRoar 项目中实现**局域网零配置自动服务发现**所遭遇的底层技术瓶颈、踩坑记录及最终采用的 **UDP 广播发现方案**。供后续维护与新项目规避相同问题参考。

---

## 1. 原生的 mDNS (DNS-SD) 方案瓶颈

项目初期曾采用 Android 官方推荐的 `NsdManager`（基于 DNS-SD / mDNS 服务协议）进行服务通告与发现。在实际复杂多变的用户环境里暴露出三大弊病：

### ① 手机系统的硬件级多播包过滤策略 (Multicast Lock)
很多 Android 厂商（如华为、小米等）为了延长待机时间，其 Wi-Fi 芯片驱动底层会在手机灭屏或锁屏时**强行拦截并过滤掉局域网多播/组播包（包括 mDNS 使用的 5353 组播）**。这导致手机端根本无法接收到局域网内的 NSD 通告，除非在代码中动态申请并长时间持有 `WifiManager.MulticastLock` 锁。但这又极易被系统的电源管理策略强行杀死或抛出安全警告。

### ② `NsdServiceInfo` 的 `host` 属性被写保护
在 Android SDK 中，`NsdServiceInfo` 内部的 `setHost(InetAddress)` 方法被标记为 **`@hide`（系统隐藏 API）**。在很多 compileSdk 高而 targetSdk 不同的手机上，直接对其 `host` 属性赋值会导致在运行时抛出 `NoSuchMethodError` 或静默写失败，使得手机端读出来的 `service.host` 始终为 `null`，自动发现回填从而失效。

## 2. 踩坑记录：Docker 容器的 UDP 端口暴露机制

在服务部署于 Docker 容器的场景下，即便我们在后端容器中启动了 UDP 广播包的响应端口，如果 **`docker-compose.yml` 配置文件里没有显式对该 UDP 端口进行暴露映射**，外界的数据包同样绝对无法进入容器网关。

> [!WARNING]
> **Docker 端口配置的关键区别**：
> - 仅配置 `- "8080:8080"` 默认只会映射 **TCP** 协议端口。
> - 局域网自动发现基于 UDP，必须显式以 `udp` 后缀修饰进行端口对外暴露，例如：
>   ```yaml
>   ports:
>     - "8080:8080"
>     - "8090:8090/udp"  # 必须追加此行以放行自动发现广播
>   ```

## 3. 最终升级：UDP 广播秒级自动发现设计

我们彻底弃用了复杂且易受拦截的 `NsdManager`，转而使用更加硬朗、在局域网内几乎 100% 可达的 **UDP 广播握手方案**。

### ① 全局通信协议标准
- **UDP 广播服务端口**: **`8090`**
- **客户端广播握手载荷**: `"DISCOVER_DINOROAR_REQUEST"`
- **服务端响应格式**: `{"port": TCP_PORT}`（JSON 字符串）

### ② 客户端的双重广播发送 (Dual Broadcasting)
为应对各式路由器与多频合一 Wi-Fi 网络的隔离策略，客户端发送时应采用双重广播：
1. **通用受限广播**: 发送往 `255.255.255.255`。
2. **特定子网广播**: 动态读取 WiFi 芯片的 DHCP 分配信息，根据 `dhcp.ipAddress` 和 `dhcp.netmask` 计算出本网段的特定广播地址（如 `192.168.x.255`），向该地址再次发送广播。该方式具有极强的网关穿透能力。

### ③ 服务端动态端口拉取
服务端启动时在后台开启守护线程监听 `8090/udp` 端口。当收到客户端 of 发现指令时，**优先查询数据库 `system_settings` 的最新通告端口**，若无则使用默认值，最后回送给客户端。避免了管理员更改业务端口后，发现机制仍然回填旧端口的 Bug。

---

## 4. 经验启示

1. **涉及局域网硬件特性的逻辑，绝不能单方面依赖系统高级 API**：在 Android 系统碎片化与厂商省电拦截的大背景下，偏底层的 UDP/TCP 套接字通信远比 `NsdManager` 等高级封装框架更易调试和掌控。
2. **凡有局域网双端握手需求，首要排查 Docker 端口与防火墙规则**：Docker 容器隔离了大部分不属于默认映射的网络协议，UDP 服务必须加缀 `/udp` 映射，否则物理层连接是绝对断开的。
